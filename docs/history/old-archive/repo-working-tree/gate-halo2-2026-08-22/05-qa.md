# HALO 2.0 GauntletGate FULL — QA Engineer deep-dive

**Scope:** Runtime behavior of the four deterministic LJP scripts (`Halo-Size.ps1`,
`Halo-Plan.ps1`, `Halo-Pending.ps1`, `Halo-Coverage.ps1`) and the MAP workflow template
(`skills/large-job/map.workflow.js`), driven against adversarial inputs in an isolated
scratch directory. I did not touch `~/.dsh` or the repo working tree — every `-Path`,
`-RunDir`, `-RunsRoot`, `-OutFile` in every test below points inside my own scratchpad
(`...\5fb7f768.../scratchpad\qa\`). The one place I *read* the live deployed copy
(`C:\Users\scott\.dsh\scripts\halo\Halo-Coverage.ps1`) I only ever invoked it against my
own scratch run-dirs, never wrote to `~/.dsh`. Branch: `feat/halo2-wp2` vs `master`.

All commands below are real invocations I ran and pasted output from (PowerShell 7.6.5
unless a case explicitly says "under `powershell.exe` 5.1"). Where I did not run something
(e.g. the real dsh engine's `maxTotalAgents` behavior under an oversized manifest) I say so
explicitly and label the conclusion "plausible, unverified."

## Top-line: what I broke that matters

1. **A findings file that is valid JSON but omits the required `"status"` key is silently
   counted as SUCCESS by both the MAP loop and the mechanical COVERAGE gate.** Zero test
   coverage anywhere in the suite. This is the single biggest hole in the "COVERAGE
   mechanically decides done, never trust the model" promise.
2. **The live, currently-deployed `Halo-Coverage.ps1` is not this branch's code.** It is
   missing all three fixes G1-EVIDENCE.md and commit `c490793` claim are proven live
   (case-insensitive containment marker match, honest-report short-name matching,
   case-insensitive dedupe). Proven with two side-by-side A/B runs, and independently
   corroborated by the suite's own `V3` test, which is failing right now.
3. A `manifest.json` unit whose `units/unit-NNN.json` plan file is missing from disk
   silently drops that unit's target files from every gap-tracking mechanism.
4. Malformed/truncated JSON in `sizing.json` or `manifest.json` crashes `Halo-Plan.ps1`,
   `Halo-Pending.ps1`, and `Halo-Coverage.ps1` with an **unhandled exception (exit 1)**,
   not the documented exit 2.
5. `Halo-Plan.ps1` has no `-MaxUnits` parameter and never reads `sizing.json`'s `verdict`
   field — a SIZE `refuse` verdict is purely advisory prose; nothing downstream enforces it.

Full evidence for each below, in the order I found them.

## F1 (CRITICAL) — a status-less findings file is silently graded "ok" at BOTH layers

### The COVERAGE side

`scripts/halo/Halo-Coverage.ps1:130,133`:
```
130:    $status = 'ok'
...
133:        if ($fnd.PSObject.Properties.Name -contains 'status' -and [string]$fnd.status -ne 'ok') { $status = [string]$fnd.status }
```
`$status` defaults to `'ok'` and is only overwritten when the `status` key is **present**
and **not** `'ok'`. If the key is simply absent, `$status` stays `'ok'` — the unit lands in
`unitsSucceeded`, never in `failedUnits` or `notAttemptedUnits`, so it never has to be named
anywhere in `REPORT.md`'s gap section.

**Isolated proof** (built at `...\scratchpad\qa\isolated-status-hole\`): one unit whose
`findings/unit-000.json` is exactly
```json
{"summary":"reviewed important-security-file.ps1, looks fine"}
```
— valid JSON, has a summary, simply never sets `status`. Running the repo's own
`Halo-Coverage.ps1 -RunDir $iso` against it:
```json
{
  "unitsTotal": 1, "unitsSucceeded": 1, "unitsFailed": 0, "unitsNotAttempted": 0,
  "gapHidden": false, "gapsUnnamed": [], "complete": true
}
```
**Exit code 0.** A unit that never confirmed success is mechanically certified complete.

### The MAP-loop side (same class of bug, independently)

`skills/large-job/map.workflow.js:80`:
```js
const failed = (res === null) || (res && res.status && res.status !== 'ok');
```
If a child's returned object has no `.status` property, `res.status` is `undefined`
(falsy), so the whole expression is `false` — the unit is pushed onto `done`, not
treated as a failure.

**Live proof**, running the actual template file (not a copy) through the exact
`AsyncFunction` wrapper technique `tests/halo/Test-MapTemplate.mjs` itself uses
(script at `...\scratchpad\qa\probe-map-missing-status.mjs`, mock agent returns
`{summary: "..."}` with no `status` for `unit-001`):
```
$ node probe-map-missing-status.mjs
{ "unitsTotal": 3, "unitsDone": 3, "unitsFailed": 0, "halted": false }
unit-001 returned an object with NO "status" key.
CONFIRMED: the status-less unit was silently counted as DONE, not failed.
```

### Why this is reachable, not contrived

- `SKILL.md`'s own `findingSchema` marks `status` as `"required": ["status","summary"]` —
  the system's own spec treats it as mandatory.
- But `map.workflow.js:71-77` explicitly documents that it does **not** pass a `schema` to
  `agent()` for MAP calls ("a normal text return resolves to null and every child reads as
  'failed'... let mechanical COVERAGE be the real gate"). So `findingSchema` is read into a
  local const at line 24 and **never used again anywhere in the file** — it is dead weight,
  not an enforced contract. Nothing stops a local model from writing valid JSON that's
  missing one key, especially the exact degraded/rushed local model this whole redesign
  exists to survive.
- `Halo-Pending.ps1` (line 64) requires `status == 'ok'` to be **explicitly present** to
  call a unit done — the opposite, safer default from COVERAGE. The two gates disagree
  about what "done" means for the identical input shape.

### Test-suite check (why this slipped through)

Every findings fixture in `tests/Run-Tests.ps1` (H3, H4, H6, H11, H13) and in
`Test-MapTemplate.mjs` hardcodes an explicit `"status":"ok"` or `"status":"failed"`.
`grep -n '"status"' tests/Run-Tests.ps1` returns only `{"status":"ok"}` / `{"status":"failed"}`
literals — never a findings object that omits the key. The 35-mutation fail-closed harness
(`tests/Prove-TestsFailClosed.ps1`) only re-introduces **previously-found, already-fixed**
defects; it has no mutation for this because nobody had found it yet. "All 35 mutations
caught" is true and proves nothing about this hole (see the Test-Suite section below).

**Fix shape:** `$status` should default to `'unreadable'`/`'incomplete'`, not `'ok'`, and
only become `'ok'` when the key is explicitly present and equal to `'ok'` — mirroring
`Halo-Pending.ps1`'s own stricter check. Apply the identical fix to `map.workflow.js:80`
(`res.status === 'ok'` instead of the current truthy-then-inequality chain, so a missing key
is `undefined !== 'ok'` → failed).

**Test it:** write `findings/unit-000.json` as `{"summary":"x"}` (no `status`), run
`Halo-Coverage.ps1 -RunDir <rd>`; a fixed script must NOT report `complete:true`/exit 0.

## F3 (MAJOR) — a manifest-listed unit whose plan file is missing from disk vanishes from coverage with zero trace

Deleted `units\unit-006.json` from an otherwise-normal run while `manifest.json` still
listed `unit-006` (simulates: a disk error, an AV quarantine, a race between PLAN's write
and a later read, or PLAN's own stale-file cleanup at `Halo-Plan.ps1:167-171` racing a
locked file and silently `Write-Warning`-ing past it).

**`Halo-Pending.ps1:71-77`:**
```
71:    $files = @()
...
73:    if (Test-Path -LiteralPath $unitFile) {
74:        $u = Get-Content -LiteralPath $unitFile -Raw -Encoding UTF8 | ConvertFrom-Json
75:        $files = @($u.files | ForEach-Object {...})
76:    }
77:    $pending.Add([pscustomobject]@{ unit = $unitId; index = [int]$row.index; files = $files })
```
When the unit file is missing, `$files` stays `@()` — **no warning, no error.** Observed:
```json
{"unit":"unit-006","index":6,"files":[]}
```
`Halo-Pending.ps1` exits 0. A MAP child would receive a work item with zero file
references and be told to write findings anyway.

**`Halo-Coverage.ps1`:** the per-unit truncated-file inventory loop (lines 117-123) is
itself guarded by `if (Test-Path -LiteralPath $unitFile)` — when the unit file is gone,
that unit contributes **nothing** to `truncatedFiles`. I gave `unit-006` a plausible,
honest-looking findings file (`{"status":"ok","summary":"nothing to review, marking ok"}`)
and re-ran COVERAGE: `unit-006` landed in `unitsSucceeded`, never in
`notAttemptedUnits`, `failedUnits`, or `gapsUnnamed`. The one real source file that unit was
originally planned to review (`file6.txt`) is not named anywhere in `coverage.json`, and
`REPORT.md` was never required to mention it. (My REPORT.md in this run still hit exit 4 —
but only because of *other*, unrelated truncated files I'd left unnamed; `unit-006`'s hole
contributed zero entries to `gapsUnnamed`, which is the actual point: it is invisible to the
gate, not merely a gap the gate happens to also catch.)

**Fix shape:** if a manifest-listed unit's `units/<id>.json` cannot be read, that is itself
a gap — COVERAGE should add an explicit `"unit file missing on disk: <id>"` entry
(distinct from `notAttempted`/`failed`) so it must be named in `REPORT.md`, and
`Halo-Pending.ps1` should at minimum log a warning rather than silently emitting `files:[]`.

**Test it:** plan a run, delete one `units\unit-NNN.json`, give that unit any `status:"ok"`
findings file, run `Halo-Coverage.ps1`; the file(s) that unit covered will not appear in
`truncatedFileCount`/`gapsUnnamed` no matter what.

## F4 (MAJOR) — malformed/truncated JSON in sizing.json or manifest.json crashes 3 of the 4 scripts with an undocumented exit 1

All three consuming scripts read their required JSON input with no `try/catch`:
- `Halo-Plan.ps1:114` — `$sizing = Get-Content ... | ConvertFrom-Json`
- `Halo-Pending.ps1:46` — `$manifest = Get-Content ... | ConvertFrom-Json`
- `Halo-Coverage.ps1:96` — `$manifest = Get-Content ... | ConvertFrom-Json`

Each script's docstring promises "Exit 0 on success, 2 on bad input" and each already
has a shape-guard for a *validly-parsed-but-incomplete* object (added in commit
`78e439e` after G1's own review found the same class of bug for missing files). But a
**syntactically broken** file — the more common real-world "bad input" (a process killed
mid-write, which is exactly the situation RESUME exists to recover from) — throws before
the shape guard ever runs.

**Proof**, truncated `sizing.json` (`{ "schema":..., "files": [ { "path": "x.txt", "bytes": 10`)
against `Halo-Plan.ps1`, invoked inside `try { & script } catch { ... }` in the *caller* so
the propagation is unambiguous:
```
UNCAUGHT EXCEPTION PROPAGATED TO CALLER: Conversion from JSON failed with error:
Unexpected end when deserializing object. Path 'files[0].bytes', line 1, position 92.
LASTEXITCODE at time of catch: <empty -- the script's own exit N line never ran>
```
Identical result, same truncation technique, against `manifest.json` through both
`Halo-Pending.ps1` and `Halo-Coverage.ps1` — same uncaught exception, same missing exit
code. This is 3-for-3, not a one-off.

By contrast, all the requested "nasty input" cases that ARE already guarded work exactly as
documented: a missing file → clean exit 2 with a `[Console]::Error.WriteLine` message; valid
JSON missing `unitCount`/`units` → clean exit 2 (`"manifest is malformed (missing
unitCount/units)"`); a **findings**-file-level truncated JSON is correctly caught by
`try/catch` in both `Halo-Pending.ps1:62-67` and `Halo-Coverage.ps1:131-143` and treated as
"not done" / `'unreadable'` respectively — safe, honest, fail-open-to-retry behavior. Credit
where due: the pattern that's missing here is applied correctly one level down (findings
files), just not at the sizing/manifest level.

**Test-suite check:** `H11` (`tests/Run-Tests.ps1:664-680`) only constructs a *missing*
manifest (`New-Item -ItemType Directory`, no `manifest.json` at all) to prove exit 2. It
never constructs a syntactically-invalid-but-present one. Same toothless-test shape as F1.

**Fix shape:** wrap each of the three `ConvertFrom-Json` calls on required input files in
`try/catch`, emitting the same `[Console]::Error.WriteLine(...); exit 2` pattern already
used for missing files and bad shape.

**Test it:** truncate any valid `sizing.json`/`manifest.json` mid-object and re-run the
corresponding script; a fixed script must print a clean message and exit 2, not throw.

## F5 (MAJOR) — `Halo-Plan.ps1` has no unit-count ceiling; a SIZE `refuse` verdict is advisory only

`Halo-Size.ps1`'s `refuse` verdict exists specifically because `-MaxUnits` (default 60) is
"under the `maxTotalAgents: 64` engine cap, leaving room for the reduce children"
(`Halo-Size.ps1:33-35`, and confirmed live in `dsh/agent-presets/halo-standard/agent.cordis.yml:255`
and `halo-ljp/agent.cordis.yml:222`, both `maxTotalAgents: 64`). But:
- `Halo-Plan.ps1`'s param block (lines 46-55) has **no `-MaxUnits` parameter at all.**
- Its only input validation (lines 110-119) checks the sizing file exists and has a
  non-empty `files` array. It never reads `$sizing.verdict`.

**Proof:** 70 uniform 1000-byte files, `Halo-Size.ps1 -WindowTokens 10000 -UnitBudgetTokens
200 -MaxUnits 60`:
```
SIZE exit=3  verdict=refuse  contentTokens=20020  fitThreshold=6000  estimatedUnits=118  maxUnits=60
```
Then `Halo-Plan.ps1 -SizingFile <that sizing.json> -UnitBudgetTokens 200` (same budget, so
PLAN's real greedy packing matches SIZE's estimate closely) on the **exact file SIZE just
refused**:
```
PLAN exit: 0
manifest written: unitCount=70   (SIZE had refused at MaxUnits=60)
PLAN gave zero warning, zero error, zero reference to the refuse verdict or any unit cap.
```
Nothing downstream of SIZE ever re-checks the cap. The whole enforcement of "refuse" is
`SKILL.md` prose telling the orchestrating agent to read `sizing.json.verdict` and stop —
a purely behavioral contract, in a design that otherwise (COVERAGE) explicitly refuses to
trust model behavior for anything that matters. This is the same trust boundary the rest of
the redesign was built to eliminate, left open at exactly the step (SIZE → PLAN) that
exists to prevent the original 2026-08-20 runaway-job failure mode.

**What I did NOT verify:** whether the real dsh workflow engine's `maxTotalAgents: 64` would
itself hard-abort a 70-sequential-unit MAP loop partway through (`map.workflow.js` runs
children strictly sequentially, one at a time, so it's plausible `maxTotalAgents` counts
cumulative spawns over the run's life, not concurrency — but I did not run a live 70-unit
workflow against LM Studio to confirm; that would be an expensive, long-running,
non-deterministic test outside this pass's scope). What I verified with certainty is that
`Halo-Plan.ps1` itself enforces nothing and warns of nothing.

**Fix shape:** add `-MaxUnits` to `Halo-Plan.ps1` (default matching `Halo-Size.ps1`'s 60)
and refuse (clean non-zero exit, not a crash) to write a manifest whose `unitCount` exceeds
it, or at minimum re-check `$sizing.verdict -ne 'refuse'` before proceeding.

**Test it:** reproduce the numbers above; a fixed `Halo-Plan.ps1` must not silently succeed.

## What worked (verified, not assumed)

- Zero-byte files, files with embedded unicode + CRLF + a real UTF-8 BOM, and a 963-character
  deep path containing spaces all sized correctly with no crash, under **both** PowerShell 7.6.5
  and Windows PowerShell 5.1 (`powershell.exe`) — the deep-path case matters because the
  scripts explicitly target PS 5.1 compatibility and historical `MAX_PATH` bugs bite there
  first; none did here.
- `REPORT.md` saved as real UTF-8-with-BOM (`EF BB BF` verified byte-for-byte) is parsed
  correctly by `Get-Content -Raw -Encoding UTF8` — confirmed the BOM does not survive into
  the parsed string (first char is `#`, not U+FEFF) on both PS7 and PS 5.1.
- Findings-file-level truncated/invalid JSON is safely caught (`try/catch`) in both
  `Halo-Pending.ps1` and `Halo-Coverage.ps1`, failing open to "retry"/"unreadable" rather
  than crashing.
- Containment detection for an **exact-case** marker works correctly on the repo's current
  code, both via a findings file's `providersUsed` array and via free-text log scanning
  (`logs/*.jsonl`), each producing `exit 5`, `containmentBreached:true`, and a correct
  `providerHits` entry.
- The documented exit-code precedence — "5 wins over 4 when both apply" — holds: a run with
  both a hidden gap and a containment breach exits 5, and `coverage.json` correctly sets
  both `gapHidden:true` and `containmentBreached:true`.
- Three concurrent `Halo-Coverage.ps1` invocations against the same run dir (PowerShell
  background jobs, same default `coverage.json` target) produced no corruption, no crash,
  and a valid final file across 3 runs. Caveat: job-based concurrency has scheduling
  latency, so this is not a proof against a genuine same-tick race on
  `[System.IO.File]::WriteAllText` (not transactional) — I did not reproduce a failure, but
  I also did not achieve guaranteed nanosecond-level simultaneity.
- The 35-mutation fail-closed harness (`tests/Prove-TestsFailClosed.ps1`) does exactly what
  it claims: I ran it, all 35 historical-defect mutations were caught, ending
  `all 35 mutations caught by their own test - the suite fails closed`. **This claim is
  true as stated.** What it does NOT mean: this harness only re-injects previously-found,
  already-fixed defects. It has no mutation for F1, F3, F4, or F5 above because nobody had
  found them yet — "fails closed" here is a regression lock, not a guarantee against unknown
  classes of bug. Treat the two facts as compatible, not contradictory.
- "43 tests pass": also literally true — my full run of `tests/Run-Tests.ps1` shows exactly
  43 deterministic/static tests passing (48 total minus the 5 "live: this machine" checks).
  What's missing from that framing: the full run is **47 passed, 1 failed**, and the failure
  (`V3`) is real and is F2 above. "43 tests pass" is a true but incomplete number to have
  presented to this gate without also surfacing the one that's currently red.
