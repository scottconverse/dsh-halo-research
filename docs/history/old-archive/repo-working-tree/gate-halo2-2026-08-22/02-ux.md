## Findings

### UX-1 (Major) — The "ok" math badge has no color; the safety traffic-light is broken for the common case

**File/line:** `mission-control/mission-control.mjs:1335` (usage), `:1080-1081` (CSS).

**Expected:** The live-math line signals safe-vs-refused the same way the rest of the app signals
status — a colored badge, matching the red `badge-red` used one branch over.

**Observed (live-verified):** With the box's real, valid settings loaded (`window=131072,
thresholdRatio=0.75, retainRatio=0.5, summaryMaxTokens=12288`), `document.getElementById('set-math')
.innerHTML` is:

```
compact at <b>96K</b> · retain <b>64K</b> · summarize <b>32K</b> into <b>12K</b> = <b>2.67:1</b> <span class="badge badge-green">ok</span>
```

`getComputedStyle()` on that span returns `background-color: rgba(0,0,0,0)` and `color: rgb(238,246,255)`
— identical to `getComputedStyle(document.body).color`, i.e. plain ink, no color at all. I enumerated
every stylesheet rule in the page (`document.styleSheets`) for a selector containing `badge-green`:
none exists. Only `.badge-amber`, `.badge-red`, `.badge-teal`, `.badge-mut` are defined (line 1081).
`.badge-green` was never added.

**Cause:** Line 1335 emits `class="badge badge-green"` for the "ok" branch, but the CSS author only
defined amber/red/teal/mut variants at line 1081. `--green:#5fe39a` exists as a root token (line 1011)
and is used elsewhere (`.hero-state .st.busy`, vitals `<b>` accents) — it just was never wired into a
`.badge-green` rule.

**Why it matters:** This is the **default, everyday state** — every time the operator's numbers are
fine, which is most of the time. The one case the badge is supposed to make instantly, peripherally
scannable ("green = you're fine, don't read the sentence") is silently downgraded to plain text sitting
next to a bold red "would be refused" badge that works perfectly. The half of the traffic light that
exists to prevent a reflex second-guess is the half that's missing.

**Fix:** Add `.badge-green{background:#123a1e;color:var(--green)}` next to the other badge variants at
line 1081 (matching the existing amber/red/teal pattern: dark tint background + bright token color).

**Test:** Load `#settings` with any valid configuration, inspect `#set-math .badge` — expect a visibly
green pill matching the visual weight of the red "would be refused" badge produced by an invalid edit.

### UX-2 (Major) — Settings inputs have no accessible label and no input type

**File/line:** `mission-control/mission-control.mjs:1290` (text inputs), `:1288` (select),
`:1307-1309` (row markup).

**Expected:** Per the brief's own question — "are the inputs labelled and typed correctly" — each of
the 7 controls should be programmatically associated with its row label and typed for its data (number
vs. enum).

**Observed (live-verified):** Ran this against the live DOM:

```js
Array.from(document.querySelectorAll('#settings-body [data-wl]')).map(i => ({
  wl: i.getAttribute('data-wl'), tag: i.tagName, type: i.getAttribute('type'), id: i.id, hasLabel: !!i.closest('label')
}))
```

All 7 controls (`contextWindow`, `thresholdRatio`, `retainRatio`, `summaryMaxTokens`,
`streamIdleTimeoutMs`, `maxRetries`, `reasoning`) came back with `type: null` (i.e. the attribute is
absent — default text/select, no numeric semantics), `id: null`, `hasLabel: false`.
`document.querySelectorAll('#settings-body label').length === 0` and
`aria-label`/`aria-labelledby` count across all 7 controls is `0`. The label association is the visual
adjacency of a `<td class="mut">` text cell next to a `<td>` input cell (line 1308) — real for a sighted
mouse user reading left-to-right, nonexistent for a screen reader, which announces each control with no
indication of which of the 7 settings it is.

Concretely, the 4 numeric fields (`contextWindow`, `summaryMaxTokens`, `streamIdleTimeoutMs`,
`maxRetries`) and the 2 ratio fields (`thresholdRatio`, `retainRatio`) are all plain `<input>` with no
`type="number"`, no `min`/`max`/`step`, and no `placeholder` hinting the valid range. A ratio field's
valid range (strictly between 0 and 1) is discoverable only by typing an out-of-range value and reading
the resulting error (`applySettings`, server-side) — there is no proactive hint anywhere in the UI.

**Cause:** `settingsInput()` (lines 1284-1291) builds bare `<input data-wl="…">` / `<select
data-wl="…">` elements addressed only by a custom `data-wl` attribute (used by the JS, not by
assistive tech), with row labels rendered as plain `<td>` text instead of `<label for="…">`.

**Fix:** Give each input a real `id` (e.g. `set-in-contextWindow`), wrap or pair the label cell with
`<label for="set-in-contextWindow">`, and add `type="number"` + sane `min`/`step` to the 4 integer
fields and `type="number" step="0.01" min="0" max="1"` (exclusive bounds still enforced server-side) to
the 2 ratio fields. That alone gets numeric keyboards on touch, native browser range nudging, and a
correctly-announced label for screen readers at near-zero cost.

**Test:** Tab through the Settings form with a screen reader (NVDA/Narrator) — each control should
announce its setting name, not just "edit text."

### UX-3 (Major) — Navigating away from Settings and back silently discards unapplied edits

**File/line:** `mission-control/mission-control.mjs:1359-1367` (`onTabShown`), `:1292-1317`
(`loadSettings`, full `innerHTML` replace).

**Expected:** Given this brief's explicit question ("is there any way to lose your edits silently") and
this exact codebase's own established pattern for anything consequential — `stopSession()` (line 1378)
gates a destructive click behind `confirm(...)` — some equivalent guard should exist before an
in-progress multi-field edit is thrown away.

**Observed (live-reproduced):**
1. On `#settings`, set the Context window input to `99999` via a real `input` event. `settingsRecalc()`
   fires; Apply button reads **"Apply 1 change"**, enabled.
2. Clicked the **Overview** tab button, then clicked the **Settings** tab button again (both real
   clicks on the actual `<button class="tabbtn">` elements).
3. Re-read the DOM: the Context window input's value is back to **`131072`** (the on-disk value), and
   the Apply button reads **"Apply changes"**, disabled again. No dialog, no toast, no "you have unsaved
   changes" indicator appeared at any point in this sequence.

**Cause:** `document.querySelectorAll('.tabbtn')[...].addEventListener('click', ...location.hash=...)`
→ `hashchange` → `showTab()` → `onTabShown('settings')` → `loadSettings()` unconditionally. `loadSettings`
does `el.innerHTML = tbl + …` (line 1310) — a full replace of the settings DOM subtree, including all 7
`data-orig` values, every time the tab becomes active, with no check for whether `settingsGather()`
currently reports pending changes. (The 5-second master poll at line 2676-2681 correctly does **not**
include `settings` in its list of tabs to refresh, so this is not a background-timer problem — it's
specifically triggered by revisiting the tab.)

**Why it matters:** This is the single most-used tab-switching pattern imaginable — an operator tuning
several related values (say, `thresholdRatio` and `retainRatio` together, since the math line is what
tells them if the pair is safe) glances at Overview or System mid-edit to check something, comes back,
and the work is gone with zero indication anything happened. Given the entire feature exists because a
config mistake caused a 4h41m failed run, an editing surface that can quietly eat your draft undermines
exactly the trust this tab is supposed to build.

**Fix:** Either (a) skip the `loadSettings()` re-fetch when returning to an already-initialized
`#settings-body` that has pending changes (compare against `settingsGather()`), and only hard-reload on
first load or after a successful Apply; or (b) if a re-fetch on every visit is intentional, add a
`beforeunload`-style guard — a `confirm()` (matching `stopSession`'s existing pattern) fired from the
tab-switch handler when `Object.keys(settingsGather()).length > 0` and the destination isn't Settings.

**Test:** Type a new value into any Settings field, switch to any other tab, switch back — the typed
value and the "Apply N changes" state should either persist or the switch should be interceptable with
a warning. Currently neither happens.

### UX-4 (Minor) — The live-math line can render negative, nonsensical token counts instead of an invalid-state placeholder

**File/line:** `mission-control/mission-control.mjs:1329,1335` (client), mirrored server-side at the
`computeSettings()` function (search `const compactAt = … Math.round(window * thresholdRatio)`).

**Expected:** The math line's entire purpose (per its own intro copy, line 1200: "the compaction math
they produce") is to make the consequence of a change legible at a glance. An impossible value (you
cannot "summarize" a negative number of tokens) should read as invalid, not as a number.

**Observed (live-reproduced):** Set `retainRatio` to `0.9` (above the real `thresholdRatio` of `0.75`)
via a real `input` event. `#set-math` rendered:

```
compact at 96K · retain 115.2K · summarize -19.2K into 12K = -1.6:1  [would be refused]
```

`toSum = compactAt - retain` (line 1329) has no floor at zero, and the ratio computed from it
(`toSum/sMax`) inherits the sign. The red "would be refused" badge and the refusal card below it (which
*is* clear — see credit above) are both correct and present, so the operator is not misled about the
outcome — but the number line directly above the correct explanation is displaying "-19.2K into 12K =
-1.6:1," which reads as broken math at the exact moment (an invalid edit) the tool most needs to look
trustworthy.

**Fix:** When `toSum < 0` (or more generally, when `refs.length > 0`), render the math line's derived
figures as `fmtK(null)` (the existing "—" fallback already used for a null ratio) instead of the raw
arithmetic, e.g. `compact at 96K · retain 115.2K · — invalid, retain exceeds compact-at —`.

**Test:** Set retain ratio above threshold ratio live; read `#set-math` — expect no negative numbers.

### UX-5 (Minor) — The disabled Apply button gives screen-reader/keyboard users no reason for being disabled

**File/line:** `mission-control/mission-control.mjs:1313` (button markup), `:1338`
(`ab.disabled=…` with no accompanying `title`/`aria-*`).

**Expected:** Per the brief — "is the Apply button's disabled state discoverable" — for *any* input
mode, not just sighted mouse use.

**Observed (live-verified):** With a refused edit staged (`retainRatio=0.9` scenario above),
`document.getElementById('set-apply')` has `disabled: true`, `style.opacity: "0.5"`, and
`getAttribute('title') / getAttribute('aria-disabled') / getAttribute('aria-describedby')` are all
`null`. A sighted mouse user connects the dimmed button to the red card above it visually. A
screen-reader or keyboard-only user tabbing to the button hears only "Apply changes, dimmed/unavailable"
with no link to *why* — the refusal list in `#set-ref` (line 1312) is a sibling `<div>`, not referenced
by the button at all.

**Fix:** Add `ab.setAttribute('aria-describedby','set-ref')` alongside the existing disable logic at
line 1338 (the `#set-ref` id already exists and already holds the human-readable reason when refused).

**Test:** With NVDA/Narrator active, tab to a disabled Apply button after staging a refused edit —
expect the refusal text to be announced, not just "dimmed."

### UX-6 (Minor) — Settings' error/unavailable state uses neutral gray, inconsistent with this app's own red-for-degraded convention

**File/line:** `mission-control/mission-control.mjs:1296` (`d.error` branch),
`:1316` (fetch-failure `catch`), compare `:2175` (memory graph's degraded state).

**Expected:** A broken data fetch reads as broken, consistently with how the rest of the app already
signals it.

**Observed (read, not forced live — see "could not assess"):** Both Settings error paths render

**Fix:** Match the existing convention: wrap both Settings error messages in
`style="color:var(--red)"` (or a `v-bad`/red badge), consistent with line 2175.

**Test:** Not run live (would require making `settings.yaml` unreadable or the API unreachable on the
live box, out of scope for a read-only pass) — this is a static-code comparison against an existing,
working pattern in the same file, not a reproduced defect.

### UX-7 (Minor) — Refusal copy leans on undecoded internal shorthand (F2/F3/G5/G7) with no in-UI glossary

**File/line:** `mission-control/mission-control.mjs:1200` (intro, "G5"/"G7"), `:1331-1333`
(refusals, "F3"/"F2").

**Observed:** The intro paragraph and every refusal string tag itself with a bare code —
`"…(F3)."`, `"…re-arms the retry storm (F2)."`, `"...refusal checks (G5)"`, `"...no YAML editing (G7)"`
— with no tooltip, link, or expandable note anywhere in Mission Control explaining what F2/F3/G5/G7

operator-facing surface, and "no assistant, no YAML editing (G7)" in particular reads ambiguously on
first pass (easy to misread as "these are unavailable" rather than "you need neither").

**Fix:** Low cost, low priority: either drop the parenthetical codes from the user-facing strings, or
make them a `title="…"` tooltip on the code itself so hovering/inspecting explains the tag without
cluttering the sentence.

### UX-9 (Nit) — No double-submit guard on Apply (identified via code reading only, not clicked live)

**File/line:** `mission-control/mission-control.mjs:1340-1350` (`applySettingsChanges`).

The function never sets `ab.disabled = true` at its own start; the button is only re-evaluated by
`settingsRecalc()`, which nothing in this function calls before the `await postAction(...)`. A fast
double-click could fire two overlapping `POST /api/action/apply-settings` requests, each independently
reading-modifying-writing `settings.yaml` — the second could clobber the first based on stale content
it read before the first request's write landed. I did not click Apply (out of scope for a read-only
pass), so this is a plausible race identified by reading the code, not a reproduced defect. Low
priority given the server already writes a `.mc-bak` copy before each write.

**Fix:** `ab.disabled = true;` as the first line of `applySettingsChanges()`, restored by the following
`loadSettings()` refresh.

### UX-11 (Nit) — Live math preview and server-side gate are two hand-synced copies of the same refusal rules

`settingsRecalc()` (client, lines 1326-1339) re-implements the three refusal checks — retain-vs-threshold,
summary ratio > 4, idle timeout < 600000 — independently of `computeSettings()` (server-side, same
three checks). They agree today because I compared them line-for-line. If a future change adds or
edits a rule server-side and the client copy isn't updated in lockstep, the green/red badge in
`#set-math` would show one verdict while `POST /api/action/apply-settings` returns another — the
"live-math line" this whole tab exists to make trustworthy would itself become the thing lying to the
operator. Worth a comment at both sites pointing at each other, or extracting one shared rule table.

## Summary

**Top 5:**
1. **(Major)** `.badge-green` CSS class doesn't exist — the "ok" state of the live-math line has zero

   live-verified via DOM query; a screen reader gets zero indication which field is which.
   `mission-control.mjs:1284-1291`.
3. **(Major)** Switching tabs away from Settings and back silently reverts any unapplied edits with no
   warning — live-reproduced (typed 99999, tab away, tab back, value and Apply-button state both
   reverted). No `confirm()` guard, unlike this same file's own `stopSession()` pattern.
   `mission-control.mjs:1359-1367`, `:1292-1317`.
4. **(Minor)** The math line can display negative token counts ("summarize -19.2K into 12K = -1.6:1")
   for an invalid edit instead of an invalid-state placeholder — live-reproduced.

   reason — live-verified; sighted users are unaffected (reason is visually adjacent), screen-reader
   users get no explanation.

No Blocker or Critical findings in this lane. On the author's "43 tests / 35 mutations, fails closed"
claim: that suite (`tests/halo/Test-Settings.mjs`) tests only the extracted, pure server-side
`computeSettings`/`applySettings` functions — it never touches the browser-rendered HTML/CSS/JS in the
`PAGE` template literal. None of the four live-reproduced findings above (missing badge color,
unlabeled inputs, silent edit loss, negative-number display) are reachable by that suite; "tests pass"
is a true but narrow claim that says nothing about what the operator actually sees in this tab. What
does work, verified live: the ~20s hot-reload caveat is never omitted from a success message, keyboard
focus is never stripped, and the tab lays out with no horizontal overflow at 375px mobile width.
