## Original description

Implements #6 with a base+overlay design rather than templates:

- **HALO is the base profile.** On HALO the deploy uses repo files byte-for-byte, exactly as before (proof: post-change deploy on live HALO ran green, all audit rows PASS, machine marker written as "halo"). Sync-FromLive on HALO stays a clean two-way street - the reason templates were rejected: sync cannot un-render a template, and that asymmetry would infect the base machine.
- **Non-HALO machines** deploy with `MACHINE=<name>` (first time; the box then remembers via `~\.dsh\machine`). The deploy copies the mapped files, applies `machines/<name>.yml` literal replacements to the rendered copy, and every later stage (drift guard, validation, backup, apply) runs against the render. A replacement whose `find` no longer exists in master fails the deploy loudly - profiles cannot rot silently as master moves.
- **machines/5070ti.yml** captures the full port adaptation from the TESTER record: suffixed identities everywhere (brain AND worker, so federation cannot cross-resolve), Q3_K_XL weights, ctx 32768 with the exact-match assert converted to a floor check (server auto-sizes), MTP off, KV q8_0. 18 replacements, all verified to match current master, rendered loaders pass node --check, spot-checks confirm suffixing and no leftover unsuffixed identities.
- machines/README.md documents the design and the rules (portable fixes land once in base; port boxes update their profile instead of running Sync-FromLive against adapted files).

**Honest scope:** the render mechanics are test-proven on HALO in isolation; a MACHINE=5070ti deploy has not yet run on the Blackwell box itself (its live files were hand-adapted before this existed). Its first profile-driven deploy is the remaining validation step - the drift guard will flag the hand-edited files, which is correct and expected; DEPLOY_FORCE=1 is the documented path for that one conversion deploy.
