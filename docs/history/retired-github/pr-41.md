## Original description

Root cause of the 2026-08-20 repo review that ran 4h41m on one turn without finishing. Both are regressions from doubling the window on 08-19 without re-tuning what scales with it.

**`streamIdleTimeoutMs` 300000 -> 1200000.** The 5-minute default is now shorter than a healthy first token at depth — measured TTFT 259s / 362s / 403s. The adapter killed live requests, retried, and re-prefilled the whole context each time: **2,396,400 input tokens on one turn**, 13 retries all logged `pi-ai stream idle timeout after 300000ms`.

**`compaction-basic` budgets.** Defaults ask for ~84,000 tokens folded into 8,192 (10:1). Every checkpoint came back `summarization truncated at the token cap (incomplete checkpoint)`, context never shrank, threshold re-crossed instantly — **5 failed compactions in one turn, ~95 minutes**.

Raising `maxTokens` alone makes it worse: at ~11 tok/s, summary length *is* the cost (8192 tokens ≈ 12 min, matching observed compaction durations). So shrink the input instead:

| | before | after |
|---|---|---|
| threshold | 0.8 → 104,857 | 0.75 → 98,304 |
| retain | 0.16 → 20,971 | 0.5 → 65,536 |
| summarize | ~84,000 into 8,192 (10:1) | 32,768 into 12,288 (2.7:1) |

`retainRatio`, not `retainTokens` — an absolute 65,536 exceeds the 5070Ti's entire 40,448 window and would make retain ≥ threshold there. Verified both resolve valid:

```
HALO    131072 -> compact 98304, retain 65536, summarize 32768 into 12288  OK
5070ti   32768 -> compact 24576, retain 16384, summarize  8192 into 12288  OK
```

Compaction stays expensive at this window by nature. It is a safety net, not a workflow.
