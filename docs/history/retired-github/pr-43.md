**The stack has never worked for a stranger.** Three defects, found from one live "why won't it load" report plus two clean-context adversarial audits. All verified fixed on hardware.

## 1. The loaders imported an SDK that is not in this repository

```
import { LMStudioClient } from "./vendor/node_modules/@lmstudio/sdk/...";
```

`git ls-files lmstudio/` returns **three files**. No `vendor/`. Not in the deploy map, and `.gitignore` excludes `node_modules` so it could never be committed. It existed only on my disk. Every clone died with `MODULE_NOT_FOUND`, the launcher retried twice, and the cockpit opened with no brain.

The vendored copy was **also not stock** — same version string (1.5.0), 794,178 bytes vs npm's 749,089, and it understood **eleven** load-config keys the published package does not:

| key | vendored | public 1.5.0 |
|---|---|---|
| `speculativeDraftMtp` | ✓ | **dropped** |
| `contextCheckpoints` | ✓ | **dropped** |
| `physicalBatchSize` | ✓ | **dropped** |
| `maxParallelPredictions` | ✓ | **dropped** |
| + 7 more | ✓ | **dropped** |

So `npm i @lmstudio/sdk` alone would load the brain with MTP off and wrong batch size and parallelism, **while reporting success**. That is issue #14 — never a port-box quirk, it was everyone's problem.

**Fix:** stock public SDK pinned in `lmstudio/package.json`, installed by a new deploy stage that also *proves* the loaders resolve the import on that machine; a wire-level shim pushing the dropped fields into the KV config; verification from `lms ps --json` instead of `getLoadConfig()` (which on public 1.5.0 returns all-undefined fields, so the old assert unloaded a correctly-loaded model).

**Proven:** `vendor/` renamed away entirely, then both loaders run clean.
```
brain : contextLength 131072, Q5_K_XL, parallel 1
worker: contextLength 32768,  parallel 1
```
`parallel: 1` can only arrive through the shim — the public SDK discards it.

## 2. My username was hardcoded into four deployed files

`MEMORY_FILE_PATH: 'C:\Users\scott\.dsh\memory\memory.json'` in `cordis.patch.yml` + three overlays. Default profile is `halo`, which deploys byte-for-byte; the 5070ti profile doesn't patch it. Per our own README a bad MCP row can crash the harness boot. Now derived from `$USERPROFILE`. `Snapshot-Memory.ps1` already did this correctly — it was a bug against the repo's own convention.

## 3. Both launchers hid the failures they existed to report

`Start-DSH.ps1` ran the server with no redirect, discarding its output — shipped in a commit titled *"no silent failures"*. Adversarial review found nine more: TCP-listen readiness (rc.7 deadlocks with the port held open), no identity check, browser opened on a dead port, no single-instance guard (a second double-click force-killed the first run's server — reproduced), cleanup querying only `node.exe` while the comment named `cmd.exe`, cleanup killing a deliberate second instance, missing prerequisites bypassing redirection, workspace falling back to the whole home directory under `danger-full-access`, and a UTF-16/NativeCommandError log bug I introduced mid-fix and caught by re-reading the log.

`Start-MissionControl.ps1` claimed *"browser only when serving"* on line 1 and opened it unconditionally.

**Proven:** reuse-when-healthy spawns nothing · cold start serves and is identity-checked · listening-but-silent correctly judged not-serving · full deploy green, every audit row PASS · `launcher.log` now plain readable ASCII.

Closes #14
