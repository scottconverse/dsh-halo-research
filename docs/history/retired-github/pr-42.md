**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Use a tokenizer-safe upper bound for sizing**

The `chars/3.5` estimate is not pessimistic for token-dense inputs such as minified code, punctuation-heavy data, or CJK text, where a token can represent substantially fewer than 3.5 characters. Near the 60% boundary this underestimates the job and can incorrectly permit `single-pass`, while the same estimate can also overfill planned units. Use the destination model's tokenizer or a genuinely conservative bound that also reserves harness, tool, brief, reasoning, and output tokens.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Enforce planned byte caps before child reads**

For any file larger than a unit budget, the manifest records a byte cap but the child is directed to read the original file through its own tools; no deterministic component actually applies that cap. The child can therefore ingest the full oversized file, overflow the supposedly bounded context, and produce coverage that disagrees with what was really read. Materialize capped inputs or require all reads through a wrapper that enforces the manifest ranges.
