FINDING 01

DSH already speaks to local servers

The stock web profile mounts dsh-llm-pi-ai, which implements openai-completions, takes a per-model baseURL, and discovers models via GET /models. A local-model workstation is a configuration exercise, not an engineering one.

FINDING 02

The plugin count is 133, not 227

227 packages exist in the repo; the CLI declares 62 direct dependencies; the composed default web profile mounts 133. Three different numbers, routinely conflated.

FINDING 03

Windows containment is real and already on

Default mode is workspace-write. On Windows it is a restricted-token spawn with capability-SID ACLs, ~115 KB of Win32 FFI. Upstream rates its enforcement partial, not full.

FINDING 04

ROCm now supports this exact box

ROCm 7.14.0 lists gfx1151 on Windows 11 25H2 — precisely this machine. An LM Studio ROCm runtime at the same llama.cpp version made a controlled backend comparison possible.

FINDING 05

"96 GB VRAM" is three claims in one

96 GB is the maximum carve-out. With VGM at 64 GB the GPU already addresses 99.84 GiB. The limit that actually bites is the 54.40 GiB maximum single allocation.

FINDING 06

ROCm wins prefill; Vulkan wins on memory shape

Replicated at n=4: ROCm is 2.93× faster to first token at 1.5 K tokens. But it holds 46.60 GiB at an ordinary 32 KB prompt against Vulkan's 29.35 GiB, and its footprint grows where Vulkan's stays flat. Vulkan is the default.

The largest risk is not technical

DSH's stock default model is deepseek-official / deepseek-v4-flash — a cloud provider. A workstation that appears to work perfectly can be doing none of its work locally. The only test that cannot be faked is disconnecting the network and re-running the task.

Roughly 94 of the 227 packages are not in the stock web profile at all — they are alternates, test support, or infrastructure. The static bundle-patch parse and the live --dump-default-config agree, which is why these numbers are stated with confidence.

On "200+ plugins"

The claim is defensible only as "packages published under the @deepseek-ai scope". It is not the number a user can exercise, and it is not the number that load. When sizing work against this platform, 133 is the number that matters.

Capabilities worth knowing about

  • subagent-claude-code and subagent-codex exist — DSH can delegate to other harnesses. Not mounted by default.
  • code-runtime-python — Code Mode has a Python runtime, not just a worker thread.
  • session-query-sqlite is mounted: sessions are queryable, not merely replayable.
  • tool-ralph — a dedicated loop-until-done driver.
  • spill-local — context spilling, keeping large bodies out of the window.
  • token-meter — real token accounting, mounted by default.

Zero WSL references anywhere. DSH does not treat WSL as its Windows story — it ships a native one.

The sandbox is genuine

sandbox-local selects a runner chain by functional probe, typed 'bwrap' | 'landlock' | 'seatbelt' | 'windows-acl'. The Windows backend is ~115 KB across 12 files — ffi.ts, win32-abi.ts, token.ts, acl.ts — calling GetNamedSecurityInfoW and SetEntriesInAclW to build explicit-access entries against a capability SID.

But enforcement is partial, by upstream's own admission

From docs/subsystems/sandbox.md: the Windows ACL runner "grants no explicit writable root and reports partial enforcement for its ambient ACL gaps", with "Everyone/hard-link boundaries" named as current gaps. Windows containment here is real and worth having — it is not an absolute boundary and must not be treated as one.

The bash seam — a corrected finding

Retraction

An earlier version of this report claimed a high-severity containment defect here: that tool-bash was mounted in the stock profile, and that because bash on this box resolved to a failing WSL alias, tool calls would either fail or silently escape the Windows sandbox into a Linux VM. That finding was wrong. It is retracted here rather than quietly deleted.

The error was methodological: the check matched package names in the composed plugin list and never read the disabled key on the row. Presence in the tree is not the same as being active — exactly the distinction §04 makes about plugin counts, applied to counting and then not applied here.

What the source actually says, in packages/bundle/base/cordis.patch.yml:

- id: bash-sandbox
  name: '@deepseek-ai/dsh-bash-sandbox'
  disabled: !!js process.platform === 'win32'

- id: tool-bash
  name: '@deepseek-ai/dsh-tool-bash'
  disabled: !!js process.platform === 'win32'

- id: pwsh-sandbox
  name: '@deepseek-ai/dsh-pwsh-sandbox'
  disabled: !!js process.platform !== 'win32'

- id: tool-pwsh
  name: '@deepseek-ai/dsh-tool-pwsh'
  disabled: !!js process.platform !== 'win32'

The web-app bundle then disables the host-level tool-bash and tool-pwsh rows outright, because agent presets own the model-facing tool rows — and the agent presets deployed on this machine repeat the same platform gate.

On Windows the agent is given tool-pwsh backed by pwsh-sandbox, and no bash tool at all. The gate holds at the base bundle, the mode bundle, and the preset. There is nothing to fix and nothing to disable. This is a point in the platform's favour, not a defect.

A real machine fault, found while chasing the retracted finding — and fixed

Independent of DSH, this box had a genuinely damaged WSL installation. bash failed with "The file cannot be accessed by the system."

The first reading — that the alias stub was a broken 0-byte reparse point — was also wrong: it is 0 bytes with no visible target, but so is every working alias, including winget.exe and notepad.exe. Stub size proves nothing. Invoking the stubs directly by full path, so PATH order cannot mask the result, isolated it:

winget.exeDesktopAppInstaller — Okworks
wsl.exeWindowsSubsystemForLinux — Modified, NeedsRemediationfails
bash.exesame packagefails

The alias mechanism was healthy. Both aliases belonging to the WSL package were dead, and Windows had already flagged that package for remediation. wsl appeared to work only because a real C:\windows\system32\wsl.exe exists and wins on PATH before the alias is consulted — so the damage was invisible from the command that would normally reveal it.

The fix that was rejected

Putting C:\Program Files\Git\bin on PATH ahead of WindowsApps so bash would resolve to Git Bash. It would have made the symptom disappear while leaving the damaged package in place — and Git\bin carries ~40 msys binaries (find.exe, sort.exe, echo.exe, tee.exe) that shadow Windows built-ins. Git's own installer defaults to Git\cmd precisely to avoid this. A symptom-level shim that introduces a known footgun is not a fix.

The fix applied was wsl --update — Microsoft's supported remediation path:

bash made fully conformant — the second half of the fix

Repairing the WSL package made bash run. It did not make it correct. A conformance battery (bench/Test-BashConformance.ps1, 9 behaviours) found the Microsoft alias failing two of them silently — returning empty rather than erroring, which is the worse failure mode:

bash -c 'echo $1' _ hello      # printed nothing — trailing args dropped
echo hi | bash -c 'read x'     # x empty — piped stdin dropped

Both reproduce from PowerShell and from cmd.exe, and both work through wsl -e bash — so the defect is the alias, not the harness. WindowsApps\bash.exe is Microsoft's deprecated WSL1-era entry point, superseded by wsl.exe.

Two instincts the battery proved wrong

Putting Git\bin on PATH was rejected for dragging ~40 msys binaries that shadow Windows built-ins — correct, but the narrower objection is that it was never necessary. And the .cmd shim, the obvious fix, trades one silent failure for another: it repairs arguments and stdin while corrupting quoted strings. Neither would have been caught without measuring.

C:\Users\scott\.local\bin\bash.exe    (compiled forwarder, 136 KB)
C:\Users\scott\.local\bin\bash.shim   path = "C:\Windows\Sysnative\wsl.exe"
                                      args = -e bash
  • Sysnative, not System32. The forwarder is 32-bit, so System32 is WOW64-redirected to SysWOW64 where wsl.exe does not exist — the shim reported "Could not create process" until the path changed.
  • .local\bin, not scoop\shims. On the user PATH at index 3, ahead of WindowsApps at index 9, and not scoop-managed, so a scoop update cannot remove it.
  • WSL bash, not Git Bash. Both score 9/9 but are not interchangeable — WSL sees /mnt/c/..., Git Bash sees /c/.... bash already meant WSL bash here, so preserving that avoids silently changing the filesystem namespace under anything already calling it.

Verified: where bash from a fresh shell resolves to the shim first; 9/9 conformance against PATH-resolved bash; quoting, nested quotes, paths with spaces, multi-argument passing, exit codes and Windows-drive read/write all correct; wsl, Git Bash and the shadowed MS alias all still work; user PATH byte-identical to backup.

One property worth knowing, which predates this change

bash runs as root (uid 0) inside the distro, because /etc/wsl.conf has no [user] section — even though a scott account (uid 1000) exists. This is how wsl -e bash already behaved and is not a consequence of the shim. Recorded rather than changed: the fix is a [user] / default=scott block, but files already created under /root would stop being reachable by default, and this distro reportedly hosts other work. That call belongs to the operator.

An unplanned consequence worth recording

The repair moved the WSL2 kernel from 6.6.87.2 to 6.18.33.2, because the damaged package had been stuck. AMD's Strix Halo guidance states that gfx1151 requires Linux 6.18.4 or later on distributions without a vendor-patched kernel. The old kernel was far below every such floor; the new one clears the general case.

This does not make ROCm-in-WSL a recommendation — §19 still rejects WSL as a primary execution environment, GPU access inside WSL goes through /dev/dxg paravirtualization rather than the native driver path, and none of it was tested here. It means the kernel is no longer the blocker if a Linux comparison lane is ever wanted. An observation, not a plan.

D-2 — tmux-context cannot work natively

tmux does not exist on native Windows. The package is not in the stock composition, so this is latent rather than live — but any profile adding it will not function.

65,360 + 48,938 = 114,298, exactly. Windows' "Display Memory" is simply dedicated plus shared.

The asymmetry that decides everything

AMD's own Strix Halo optimization guidance says to keep the firmware VRAM reservation minimal (as low as 0.5 GB) and raise the GTT limit instead, because "AI frameworks work more efficiently with GTT-backed allocations." That entire page is Linux-only — its mechanism is the TTM pages_limit sysfs knob and the amd-ttm helper. There is no TTM on Windows. On Linux you tune GTT and leave VRAM tiny; on Windows the carve-out is the tuning knob, because the flexible half is not user-controllable.

The four memory questions, answered

What does VGM actually do? It moves the firmware boundary between memory Windows can see and memory presented to the GPU as dedicated VRAM, applied before Windows boots. It creates no bandwidth.

Is ~96 GB a real ceiling? No — three things are being conflated. 96 GB is the maximum carve-out AMD exposes on a 128 GB part. It is not the addressable ceiling: with VGM at only 64 GB, OpenCL already reports 99.84 GiB global memory. The ceiling that actually bites first is the 54.40 GiB maximum single allocation.

Can workloads exceed the carve-out? Yes, and this machine proves it — VGM is 64 GB, OpenCL global memory is 99.84 GiB. The surplus is the shared/GTT-equivalent mapping, available but subject to eviction, so available rather than equivalent.

What setting should this machine use? Leave it at 64 GB. The resident model uses 26.73 GB with zero spill to shared memory; nothing measured is limited by the carve-out; and 96 GB would leave Windows only ~32 GB while this box also runs a browser, an IDE and the harness.

Sampled again during a 45 K-token prefill, the figure was unchanged at 26.73 GB with zero shared usage — which proves llama.cpp preallocates the full 131 K KV cache at load and it does not grow with use.

Why the KV cache is so small — architecture, not luck

Qwen3.8-27B is a hybrid: "16 × (3 × (Gated DeltaNet → FFN) → 1 × (Gated Attention → FFN))". Of 64 layers, only 16 carry full attention; the other 48 are Gated DeltaNet, whose state is constant-size rather than growing with sequence length. A conventional 27B with 64 full-attention layers at 131 K would need roughly six times the KV cache. This model is unusually well suited to long-context agent work on a bandwidth-limited part.

The real finding is shape, not a single ratio

Vulkan's footprint is flat — 29.35 GiB after a 32 KB prompt and 29.35 GiB after a 45 K-token prompt, because llama.cpp preallocates the whole KV cache at load (§08). Prompt size does not move it.

ROCm's grows with the prompt — 46.60 GiB at 32 KB, rising through 64.79 → 69.57 → 78.39 GiB mid-rung at 45 K tokens, eventually exceeding the 63.83 GiB dedicated carve-out and driving free system RAM to 1.55 GB.

The 46.60 GiB figure was identical across all three ROCm repeats — a reproducible structural property, not a transient. And it appears at ordinary prompt sizes, so it is not an artefact of the extreme 256 KB rung.

Three consequences:

  1. This contradicts the community claim that ROCm uses less memory than Vulkan. That claim almost certainly describes Linux, where AMD's GTT model applies. On Windows the memory model is different and the claim does not transfer — precisely the Linux→Windows substitution to avoid.
  2. It is a stability hazard on a working machine.
  3. It caps headroom — no second resident model, which removes the multi-model portfolio.

The mechanism was not isolated. The plausible cause is HIP compute-buffer sizing scaling with batch; community evidence points at GGML_HIP_NO_VMM=ON as a related HIP VMM defect on this GPU [community], but LM Studio's runtime does not expose that flag, so it could not be tested. Recorded as an open unknown, not as an explanation.

The deciding factor is memory shape, not throughput

ROCm wins prefill decisively and by a wide margin — that is the most solid result in this report. It loses decode, though by less than first stated and only decisively from 32 KB up, and its decode is six times noisier. It costs 1.59× the GPU memory at ordinary prompt sizes, and its footprint grows with the prompt where Vulkan's stays flat.

A backend whose working set scales with prompt size — on a machine where the carve-out is fixed at 64 GB and other software is resident — cannot be the default, however fast its prefill. Vulkan's flat 29.35 GiB is what leaves room for a second model and for the rest of the desktop.

Statistical limitations — what is and is not established

An earlier draft reported every figure from a single run per rung per backend, with no variance. That was not sufficient to support the strength of the language used.

What was done: the 8 KB and 32 KB rungs were re-run to n = 4 per backend. bench/Compute-BenchStats.ps1 aggregates the accepted CSVs, computes mean/sd/cv, and expresses each difference in units of measured noise — refusing to call anything under 3 sd decisive. The 256 KB rung was deliberately not repeated: on ROCm it drove a live machine to 1.55 GB free RAM, and re-running that on a box serving other work was not an acceptable trade.

What remains unreplicated or confounded:

  1. The 64 KB and 256 KB rungs are n = 1 on both backends. The 1.85× at 64 KB, the "parity at 45 K", and the "+106 % decode" carry no error bar.
  2. The 256 KB ROCm rung is confounded — it ran at 1.55 GB free RAM, so its prefill parity and decode collapse may be effects of the memory behaviour rather than independent findings. The first draft presented them as separate corroborating evidence. They are not.
  3. Memory figures are point samples, not a time series — independent of LM Studio, but taken at rung boundaries. The mid-rung progression is three opportunistic samples.
  4. One machine, one model, one quantization, one driver. Nothing generalises to other units.
  5. TTFT is not pure prefill. The marginal-slope method removes the fixed component, but a llama-bench microbenchmark (T-5) would isolate it properly and has not been run.

What the verdict rests on: not the long-context numbers, which are the weakest evidence here. It rests on two results that replicated cleanly at n = 4 — ROCm's large, reproducible prefill advantage in the 1.5 K–5.7 K band, and its 1.59× memory footprint at an ordinary 32 KB workload, identical across three repeats and growing where Vulkan's is flat. The second was measured at a benign workload, so it does not depend on the confounded long-context rung at all.

The machine was returned to Vulkan and verified: runtime llama.cpp-win-x86_64-vulkan-avx2@2.29.1 selected, model resident at Q5_K_XL / 131,072 / parallel 1, 19.22 GB RAM free, 29.25 GiB GPU local.

Where ROCm would still be right

Its band of advantage is real and matches a genuine workload shape: many short-to-moderate turns, each with a fresh 2–10 K prompt, where time-to-first-token dominates and total context stays small. A subagent fleet doing classification or triage looks exactly like that.

T-10 — the highest-value follow-up on this box

Load the model on ROCm at a 32 K context limit rather than 131 K, re-measure the footprint, and re-run the 8–32 KB rungs. If the working set stays under ~40 GiB, a ROCm profile becomes a legitimate second lane for short-prompt subagent work while Vulkan serves the long-context main thread.

In a probe with max_tokens: 8, the response content was empty and reasoning_tokens was 8 — the reasoning trace consumed the entire budget. Thinking mode is on by default. Any DSH tool-calling configuration must budget output tokens well above the expected answer length, or tool calls will be truncated before they are emitted.

Containment — leave it alone

The stock default is already workspace-write, resolved as process.env.DSH_PERMISSION_MODE ?? 'workspace-write'.

Do not set DSH_PERMISSION_MODE=danger-full-access

That mode does not narrow confinement — it bypasses it. From upstream's own docs: "A danger-full-access consumer spawns its original argv and does not call ctx.sandbox." One environment variable silently disables every file-effect boundary for every session, and nothing in the UI looks different afterwards. If containment matters, the check is not "is the sandbox plugin loaded" — it is loaded and inert either way — it is "what is DSH_PERMISSION_MODE set to".

The shell seam — leave it alone

No patch is required. An earlier draft instructed disabling tool-bash and bash-sandbox; that instruction rested on a false finding and is withdrawn (§06). Both rows are already disabled on win32 at the base bundle, the mode bundle, and the agent preset. Adding a user patch to disable something already disabled only adds a row to maintain.

Verify rather than assume — read the row, not the package name:

pnpm dlx "@deepseek-ai/dsh@0.1.1-rc.2" --profile web --dump-config

Confirm tool-bash carries a disabled key and tool-pwsh is the active shell row.

Verify the model is actually local

The stock composition sets provider: deepseek-official, model: deepseek-v4-flash. After configuring, confirm with both:

lms ps --json
pnpm dlx "@deepseek-ai/dsh@0.1.1-rc.2" --profile web --dump-config

The first proves which model is resident and at what quantization; the second proves what the composed profile will use. Neither can be replaced by looking at the UI.

Section 25The forty required questions

Does DSH run well natively on Windows 11, not merely launch?

Yes. Windows is a first-class target — 865 win32 references, 555 pwsh, a real Win32-FFI sandbox, zero WSL references, and the shell seam is platform-gated at three independent layers. One genuine caveat remains: sandbox enforcement self-reports partial, not full.

What capabilities are weaker or unavailable on Windows?

tmux-context (tmux does not exist natively); enforcement is partial, not full. lsp, mcp-client, e2b, subagent-codex are unknown — none is in the stock composition. tool-bash is not on this list: it is deliberately disabled on win32, with tool-pwsh active in its place.

How many first-party runtime plugins does DSH contain?

227 packages exist; the CLI declares 62 direct dependencies; the stock web profile composes 133; headless composes 78.

How many work natively on Windows?

Of the 133 composed, no Windows-specific failure was identified. The two previously flagged (tool-bash, bash-sandbox) turned out to be correctly disabled on win32 rather than broken. Stated precisely: the profile composes and boots and the high-risk packages were individually checked — all 133 were not individually exercised. This is "none found", not "all verified".

Can DSH reliably use local OpenAI-compatible servers?

Yes, out of the box. dsh-llm-pi-ai implements openai-completions, openai-responses and anthropic-messages, takes a baseURL override per provider and per model, and discovers models via GET {baseURL}/models.

Which local server is best on Strix Halo today?

LM Studio.

Is LM Studio best, or merely easiest?

Best, on the merits. It is the only candidate that switches the llama.cpp backend without a rebuild — decisive where the backend answer is workload-dependent.

Is Lemonade advantageous here?

No, not for the primary path. Its edge is NPU/hybrid execution, and there is no NPU role today. Watch.

Is direct llama-server preferable?

No for serving; yes for measurement. llama-bench isolates prefill far better than an HTTP ladder.

Does Vulkan outperform ROCm?

On decode, yes, but modestly — +14.4 % at 8 K (only 2.2 sd, suggestive) and +25.6 % at 32 K (5.3 sd, decisive), at n=4. Its bigger edge is consistency: decode cv 1.5 % vs ROCm's 9.0 %. And on memory: 29.35 vs 46.60 GiB at a matched 32 KB workload, flat where ROCm's grows.

Where does ROCm outperform Vulkan?

Prefill, decisively — 2.93× to first token at 1.5 K tokens (179 sd), 2.09× at 5.7 K (98 sd), +61.5 % marginal throughput (23 sd), all at n=4. The most solid numbers in the report. The apparent fade to parity at 45 K tokens is n=1 and confounded by memory pressure, and is not relied upon.

What ROCm works natively on Windows today?

The HIP runtime and HIP SDK for gfx1151 on Windows 11 25H2, and llama.cpp built against them.

What is still Linux-only?

The ROCm Debugger is unsupported on RDNA 3.5. TensorFlow, JAX and ONNX are Windows-absent for this part — AMD's matrix lists PyTorch as the only Windows framework for Ryzen APUs. vLLM, SGLang and training remain unknown. PyTorch itself is no longer on this list — see §09, which corrects an earlier error in this report.

What does Variable Graphics Memory actually do?

Moves the firmware boundary between memory Windows can see and memory presented to the GPU as dedicated VRAM, applied before Windows boots. Creates no bandwidth.

Is ~96 GB a real GPU-memory ceiling?

No. 96 GB is the maximum carve-out. With VGM at 64 GB this GPU already reports 99.84 GiB of OpenCL global memory. The ceiling that bites is the 54.40 GiB maximum single allocation.

Can workloads exceed the configured VGM?

Yes — proven here. VGM is 64 GB; OpenCL global memory is 99.84 GiB.

What VGM setting should this machine use?

Keep 64 GB. The resident model uses 26.73 GB with zero shared spill; 96 GB would leave Windows only ~32 GB.

How much memory should remain for Windows and DSH?

Currently 63.79 GB visible, 25.51 GB free under load. Treat 32 GB visible as the floor — exactly what the aggressive setting would leave.

Which Qwen3.8 variants exist?

Qwen3.8-27B (2026-08-14, dense, Apache 2.0), Qwen3.8-2.4T-A95B (MoE), Qwen3.8-Max (hosted). Only the 27B is relevant.

Which Qwen3.8 configuration is best for DSH?

Qwen3.8-27B, UD-Q5_K_XL, 131,072 context, parallel: 1 — the configuration already resident.

Which quantization is the best compromise?

Q5_K_XL. Above the Q4 range where code quality degrades, without paying Q6/Q8 bandwidth on a bandwidth-bound part. Confirm with T-4.

What context length is actually useful?

131,072, against a 262,144 maximum. The limit is prefill time, not memory — 45 K tokens costs 279 s to first token.

How much memory does the KV cache need at 32 K / 64 K / 128 K / 256 K?

~5.58 GB total at 131,072, preallocated at load and confirmed not to grow during a 45 K-token prefill. A per-window table was not derived — unknown (T-3).

Does Flash Attention materially improve this workload?

Partially answered. Community evidence attributes ROCm's long-context behaviour to rocWMMA Flash Attention; §10 measures the end-to-end consequence but does not isolate FA as a variable — and notably, the flat-long-context claim was not reproduced here.

Does MTP / speculative decoding materially improve this workload?

Yes — measured. Draft acceptance 5/5 observed, and decode of 14.8–16.4 tok/s exceeds the ~12 tok/s naive bandwidth ceiling for a 21.15 GB model.

Are ROCmFPX or similar specialized runtimes ready?

Unknown. No current verifiable evidence was found. Not recommended.

What other local models should be installed?

An A3B MoE worker, the existing nomic embedding model, and experimentally gpt-oss-120b. A reranker is a gap.

What is the largest model this machine can technically run?

gpt-oss-120b at 63.39 GB; addressable ceiling ~99.8 GiB with a 54.40 GiB single-allocation hazard.

What is the largest it can run usefully?

Depends on active parameters, not file size. A 63 GB dense model would decode near 4 tok/s and be useless interactively; a 63 GB MoE could be fine. Not yet measured (T-2).

What is the best primary coding/agent model?

Qwen3.8-27B UD-Q5_K_XL — dense quality, native vision, trainedForToolUse, and a hybrid architecture that makes long context affordable in memory.

Which model should handle high-quality reasoning?

gpt-oss-120b, experimental until T-2. Today the 27B in thinking mode is the practical answer.

Which smaller model for fast worker/subagent tasks?

An A3B MoE — qwen3.6-35b-a3b or qwen3-coder-30b-a3b. Small active-parameter count means far less memory traffic per token.

Should DSH dynamically route among models?

No. DSH already ships user model selection and per-subagent models. A routing layer would add a component with no measured benefit.

Can several models remain loaded simultaneously?

Yes — 26.73 GB used of a 64 GB carve-out, with ~48 GiB of shared memory beyond it. Note this headroom exists on Vulkan; ROCm's working set removes it.

Does the XDNA 2 NPU provide a useful role?

Not today. lms runtime get -l offers exactly four extensions — CPU, Vulkan, ROCm, harmony. There is no NPU option to select. Watch.

Are recent Windows builds materially improving this?

The material fact is alignment: build 26200 / 25H2 is exactly the version AMD certifies for gfx1151 ROCm support.

Are any Insider features compelling?

No. Nothing identified changes GPU memory allocation, ROCm availability or throughput. Reject for now.

What is the best daily-driver configuration?

Stock DSH web profile → LM Studio :1234 → llama.cpp 2.29.1 on Vulkan → Qwen3.8-27B Q5_K_XL @ 131 K, VGM 64 GB, sandbox workspace-write, bash seam disabled.

What should be installed only experimentally?

The 32 K-context ROCm profile, a MoE worker model, gpt-oss-120b, mcp-client/lsp/subagent-codex, and llama-bench.

What should we wait for?

An NPU runtime appearing in lms runtime get -l; PyTorch/vLLM on native Windows for gfx1151; rocWMMA improvements for RDNA 3.5; and DSH reaching a non-prerelease.

Section 27Known unknowns

Stated plainly rather than filled with speculation.

  1. Direct DSH + Strix Halo evidence is sparse. No firsthand report was found of DSH driven by a local model on this hardware. Given DSH is nine days old, that is expected — but it means this architecture is Category B (demonstrated components that compose) and Category C (hypothesis), not Category A. The DSH-side facts are strong because they come from source; the combination is not yet widely demonstrated.
  2. PyTorch / vLLM / SGLang / training on native Windows for gfx1151 — not established.
  3. Per-window KV cache table — preallocation behaviour is measured; a per-window breakdown was not derived.
  4. Why ROCm's memory footprint grows as it does — the mechanism was not isolated. GGML_HIP_NO_VMM=ON is a community-suggested lead, but LM Studio's runtime does not expose the flag.
  5. tool-fs-search without ripgrep on PATH — untested.
  6. mcp-client, lsp, e2b, subagent-codex on Windows — untested.
  7. Whether hipBLASLt / MIOpen / RCCL are Windows-available for gfx1151 specifically — the matrix gives versions, not per-OS per-target status.
  8. Whether the subagent provider-snapshot bug is fixed at the pinned commit — not independently reproduced or refuted. Treated as live.
  9. Long-run stability — nothing ran for hours. Thermal and stability behaviour under sustained agent load is unmeasured.

End-to-end UI verification remains outstanding.
