and is tested.** It is the first thing the next model should build. Design in

## 4. Hard-won operating rules — ignore these and you will repeat my week

1. **Run the self-test before any model time.** `test-harness.ps1`, 90 seconds,
   no inference. I skipped this and lost an entire working day to a one-line
   bug.
2. **Test the seams, not just the parts.** The day I lost died in a hand-off:
   the gate captured the verifier with `2>&1`, which cannot see PowerShell's
   Write-Host output, so the failure report handed to every retry round was
   **empty**. Every component passed its own test. Two more seam bugs surfaced
   later (list arguments collapsing across a `-File` boundary). Every join gets
   its own check.
3. **The worker never writes or edits its own acceptance tests.** It will
   rewrite the exam to pass. It did — on the SSRF unit it changed the spec to
   accept a private address and a mixed public/private DNS answer. Evidence:
   `gateway-conductor\evidence-frozen-catch\`. Use `-Frozen`.
4. **No model's self-report is evidence** — not the local worker's, not yours.
   Only the verifier's exit code. Re-run the suite yourself before saying
   "done".
5. **Unit sizing is the primary lever.** An oversized unit with a general brief
   fails; a micro-unit whose brief names the exact defect and quotes the
   failing assertion passes. The cache work failed six times as one 12-test
   unit and passed twice within 30 minutes once split. **A unit that fails
   twice is too big — split it, never re-run it bigger.**
6. **Briefs must be self-contained.** Never "keep the rest" — the tree may have
   been reverted.
7. **Seed every retry from that unit's preserved output, and re-verify the
   count.** Workers regress working code.
8. **One local model resident at a time.** Both loaded leaves 1.1 GB free and
   the machine crawls; one leaves 32.6 GB. (`lms load -c 32768` is silently
   ignored on this build — models load at their 262K default. Harmless for
   correctness, fatal for memory if you load two.)
9. **Killing a run:** kill the process *tree* from the pids in `gate-log.txt`,
   then verify with a 90-second artifact-silence watch. I once reported
   "stopped, all of it" from a quiet process probe while the batch ran on for
   another hour on the machine he needed.
10. **Size the work out loud before launching, and refuse an oversized
    assignment** instead of running it into his working day.
11. **Scott is point-and-click only and never uses a CLI.** Anything you build
    needs a face he can reach from the app he is already in — and you must
    tell him it exists.

## 5. The first thing to build: MCP wiring

This is the deliverable I failed to produce. It is small.

**Shape.** A local MCP server (Python or Node; `uv` and `pnpm` are both on the
box) exposing roughly:

- `halo_build(repo, brief, verify_cmd, frozen[], cap_min, rounds)` →
  `{verdict, rounds, minutes, failing_tests[], evidence_path}`.
  Implementation: shell out to `Halo-Code.ps1`, parse the exit code and the
  verdict file. The engine already writes structured evidence.
- `halo_status()` → resident models, last ledger rows, free memory.
- `halo_selftest()` → runs `test-harness.ps1`, returns the 15-check result.
- `halo_stop()` → the process-tree kill plus the silence watch from §4.9.

**Why it works everywhere.** Claude Code, Codex desktop, OpenCode and Bionic
all take MCP servers. Register once per app and every one of them can drive the
stack. Registration for the app he is in should be done *for* him, and then
demonstrated in the chat with a real build.

**Long-run caution.** A unit takes 10–25 minutes. Return a job handle
immediately and let the model poll (`halo_job(id)`), or the tool call will time
out. This is the one piece of real design work in the whole adapter.

**Acceptance test for whoever builds it:** from a fresh chat in one of those
apps, with no scripts mentioned, Scott says "build X in repo Y" and gets a
verified result back in the conversation. Until that happens, it is not done.
